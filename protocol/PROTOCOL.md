# flipper-spoolbuddy wire protocol, version 1

The Flipper app and the host (Mac now, iPad/iPhone later) exchange
newline-delimited JSON over a byte stream: USB CDC in Phase 1, BLE serial
later. The Flipper is a thin client: it sends raw tag dumps and user
actions, the host parses tags, talks to Bambuddy and sends back display
strings.

The contract is machine-checked:

- `schema/message.schema.json`: JSON Schema (draft 2020-12) for every message.
- `fixtures/messages/*.json`: at least one sample per message type, status
  and action, plus `scan_mfc_unreadable` (a MIFARE Classic whose sectors all
  failed). Files named `invalid_*` must fail the schema; every other file
  must pass.
- `fixtures/tags/*.json`: tag dumps, synthetic ones generated by
  `tools/fixtures/` and one real Phase 0 capture
  (`bambu_pla_pure_real.json`, `"synthetic": false`). `scan_*` and
  `intent_*` samples are generated from the synthetic ones by
  `tools/fixtures/make_message_fixtures.py`.

The C (`flipper/tests`), Swift (`host/`) and Python (`tools/`) test suites
all run against these files. Changing a message means changing the schema,
the fixtures, this document and both sides in one commit.

## Framing

- One JSON object per line, UTF-8, terminated by `\n` (LF). A receiver
  accepts and strips a `\r` before the `\n`. Empty lines are ignored.
- A line, including its terminating `\n`, is at most **8192 bytes**. A
  receiver drops a longer line whole (everything up to the next `\n`) and
  keeps going. A sender never produces one; the Flipper reports an encoding
  error instead.
- Senders emit compact JSON (no whitespace between tokens) and no
  non-ASCII characters on the Flipper side. Receivers accept any valid JSON
  whitespace and any key order.
- Hex strings (UIDs, ATQA, blocks, pages) are upper-case without separators.

## Common fields

| Field | Type | Meaning |
|---|---|---|
| `t` | string | Message type: `hello`, `scan`, `lookup`, `intent`, `result`. |
| `v` | integer | Protocol version, always `1`. |

A receiver ignores a line whose `t` it does not know, and a line whose `v`
is not `1`. A line that is not valid JSON, or a known `t` with missing or
ill-typed fields, is dropped as malformed; neither side crashes or
disconnects on it. Unknown fields are not allowed by the schema; a receiver
may ignore them.

## Session

1. After the transport connects, each side sends `hello` as its first line.
   On USB the Flipper sends its `hello` when the host opens the port (DTR
   raised).
2. The Flipper treats the link as **connected** once it receives a host
   `hello`. If none arrives within 2 s of its own, the port is probably held
   by something else (a terminal, qFlipper): the Flipper stays quiet, its
   status line shows `no host` and a scan stays local. A host `hello` that
   arrives later still connects. The Flipper answers a host `hello` with its
   own unless it is the reply to the Flipper's pending one. Closing the port
   loses the host.
3. Flipper → host: `scan` after each tag read.
4. Host → Flipper: `lookup` answering that `scan_id`.
5. Flipper → host: zero or more `intent`s for that scan (user actions).
6. Host → Flipper: one `result` per intent, matched by `id`.

The host may also act on a scan by itself (the owner edits the weight in the
feed); that sends nothing to the Flipper.

The host answers every valid `scan` with a `lookup`, `error` included. The
Flipper does not time out while it waits for a lookup ("Looking up"): Back
returns to Idle, and losing the host shows the scan's local facts.

## Messages

### `hello` (both directions)

| Field | Type | Required | Meaning |
|---|---|---|---|
| `app` | string, 1–40 | yes | Sender app and version: `spoolbuddy-fap/0.1.0` (Flipper), `spoolbuddy-mac/0.1.0` (Mac host), `spoolbuddy-bridge/0.1.0` (Python dev bridge). |
| `fw` | string, 1–40 | Flipper | Flipper firmware version, e.g. `1.5.1`. |
| `os` | string, 1–40 | host | Host OS, e.g. `macOS 26.0`. |

Exactly one of `fw` / `os` is present.

```json
{"t":"hello","v":1,"app":"spoolbuddy-fap/0.1.0","fw":"1.5.1"}
{"t":"hello","v":1,"app":"spoolbuddy-mac/0.1.0","os":"macOS 26.0"}
```

### `scan` (Flipper → host)

| Field | Type | Required | Meaning |
|---|---|---|---|
| `scan_id` | id | yes | Unique per scan within a Flipper app run, `s-NNNNNN`. |
| `tag` | tag object | yes | The raw dump, see below. |

Tag object:

| Field | Type | Required | Meaning |
|---|---|---|---|
| `type` | `"mfc"` \| `"ntag"` | yes | MIFARE Classic 1K or NTAG21x. |
| `uid` | hex, 4, 7 or 10 bytes | yes | Tag UID. |
| `sak` | integer 0–255 | yes | SAK from anticollision. |
| `atqa` | hex, 2 bytes | yes | ATQA as received, e.g. `0400`, `0044`. |
| `blocks` | object | `mfc` only, always present | Block number (`"0"`–`"63"`, decimal without leading zeros) → 16 bytes hex. Sector trailers (3, 7, …, 63) are never sent. Blocks of missing sectors are absent; `{}` when no sector was read. |
| `missing` | array of distinct integers 0–15 | `mfc` only, optional | Sectors that failed authentication or reading, ascending. Omitted when all sectors were read. |
| `pages` | object, non-empty | `ntag` only | Page number (`"0"`–`"230"`) → 4 bytes hex, from page 0 to the end of the tag's memory. |

The Flipper emits `blocks` / `pages` keys in ascending numeric order and tag
fields in the order of the table; `scan_mfc.json` and `scan_ntag.json` show
the exact shape.

The Flipper reads a MIFARE Classic with Key A derived from a 4-byte UID (see
`flipper/src/bambu_keys.h`). A tag those keys do not open (any non-Bambu
MIFARE Classic, or one with a 7-byte UID) is still sent, with `blocks: {}`
and all 16 sectors in `missing` (`scan_mfc_unreadable.json`); the host
matches it by UID only and offers no prefill.

```json
{"t":"scan","v":1,"scan_id":"s-000012","tag":{"type":"mfc","uid":"5A3C9E21","sak":8,"atqa":"0400","blocks":{"0":"5A3C9E21D9080400F600848E53F87010","1":"4130302D573100004746413030000000","2":"504C4100000000000000000000000000","…":"…"},"missing":[7]}}
{"t":"scan","v":1,"scan_id":"s-000013","tag":{"type":"ntag","uid":"04112233445566","sak":0,"atqa":"0044","pages":{"0":"041122BF","1":"33445566","…":"…"}}}
```

A full Bambu dump (48 data blocks) is about 2 KB, a full NTAG216 dump
(231 pages) about 4 KB, both well under the line limit.

### `lookup` (host → Flipper)

| Field | Type | Required | Meaning |
|---|---|---|---|
| `scan_id` | id | yes | The scan this answers. |
| `status` | `"found"` \| `"unknown"` \| `"error"` | yes | Spool found in Bambuddy, not found, or lookup failed. |
| `spool_id` | integer ≥ 1 | when `found` | Bambuddy spool id. |
| `prefill` | boolean | optional | `unknown` only: the tag gave enough data (at least `material`) for the Flipper to offer **New**. Absent means `false`. |
| `lines` | array of ≤ 4 strings, each ≤ 40 chars | yes | Display text, rendered verbatim. May be empty. |
| `defaults` | object | optional | Grams for the Enter weight screen: `gross` (last gross weight), `label` (filament weight per label), `core` (empty spool weight); each an integer 0–9999, each optional. |
| `error` | string, 1–200 | when `error` | Technical reason, for logs; `lines` carries what the user sees. |

The host looks a tag up with `GET /inventory/spools/by-tag`, first by the
tray UUID and then by the UID. The tray UUID of a Bambu tag is block 9 as
32 upper-case hex characters: in Phase 0 it matched, byte for byte, the
`tray_uuid` an AMS had reported to Bambuddy for the same spool. A missing
or all-zero block 9 means no tray UUID, and the lookup goes by the UID
alone. Blocks 4+5 hold the detailed type and colour, not a tray UUID. Both
parsers (Swift `TagParser`, Python `bambu_tag`) read the tray UUID the same
way, and new items and tag links store it as `tray_uuid`.

The UID the host sends to Bambuddy (the `tag_uid` of the lookup, of new
items and of tag links) is the AMS form for Bambu tags: the upper-case UID
followed by `00000100`, so `7EF1AB04` becomes `7EF1AB0400000100`. An AMS
writes `ECA8FEDE00000100` for MIFARE UID `ECA8FEDE`, and Bambuddy keeps the
last 16 hex characters of whatever it receives without padding, so this
value round-trips unchanged and spools added by an AMS and by the Flipper
match. NTAG UIDs (7 bytes) are sent as read. The `lookup` lines and the
`scan`/`intent` messages carry the UID as read.

The Flipper pre-fills the weight with `defaults.gross`, falling back to
`defaults.label + defaults.core`.

```json
{"t":"lookup","v":1,"scan_id":"s-000012","status":"found","spool_id":42,"lines":["PLA Basic","Jade White","484 g left of 1000","core 250 g"],"defaults":{"gross":734,"label":1000,"core":250}}
{"t":"lookup","v":1,"scan_id":"s-000012","status":"unknown","prefill":true,"lines":["PLA Basic","#FFFFFFFF","label 1000 g"],"defaults":{"label":1000,"core":250}}
{"t":"lookup","v":1,"scan_id":"s-000012","status":"error","lines":["Bambuddy unreachable"],"error":"connection timed out"}
```

### `intent` (Flipper → host)

| Field | Type | Required | Meaning |
|---|---|---|---|
| `id` | id | yes | Unique per intent, `i-NNNNNN`. The host's idempotency key. |
| `scan_id` | id | yes | The scan the action refers to. |
| `action` | enum | yes | `weigh`: record a weight. `new`: create a full spool from the tag (offered only when `lookup.prefill` is true). `create_on_host`: flag the feed row so the owner creates the spool on the host. `link_on_host`: flag the row so the owner links the tag to an existing spool on the host. |
| `grams` | integer 0–9999 | `weigh` | Weight typed on the Flipper. The Flipper sends it only with `weigh`. |
| `mode` | `"net"` \| `"gross"` | `weigh` | `gross`: spool on the scale as is. `net`: filament only; the host adds the spool's core weight (`gross = net + core_weight`) before `POST /spoolbuddy/scale/update-spool-weight`. The Flipper sends it only with `weigh`. |
| `tag` | tag object | yes | The same object as in the `scan`, so an intent is self-contained (a future offline queue replays intents without their scans). |

```json
{"t":"intent","v":1,"id":"i-000003","scan_id":"s-000012","action":"weigh","grams":734,"mode":"gross","tag":{"type":"mfc","uid":"5A3C9E21","…":"…"}}
{"t":"intent","v":1,"id":"i-000004","scan_id":"s-000012","action":"new","tag":{"…":"…"}}
```

### `result` (host → Flipper)

| Field | Type | Required | Meaning |
|---|---|---|---|
| `id` | id | yes | The intent this answers. |
| `ok` | boolean | yes | Whether the action succeeded. |
| `lines` | array of ≤ 4 strings, each ≤ 40 chars | yes | Display text for the Done / Error screen. |
| `error` | string, 1–200 | when `ok` is false | Technical reason, for logs. |

```json
{"t":"result","v":1,"id":"i-000003","ok":true,"lines":["Saved","484 g left"]}
{"t":"result","v":1,"id":"i-000003","ok":false,"lines":["Not saved"],"error":"spool 42 not found"}
```

## Rules

- **Idempotency.** The host remembers every intent id it has completed in
  the session and answers a repeated id with the stored `result` without
  calling Bambuddy again; a repeat that arrives while the first is still
  running waits for the same result. Results of failed Bambuddy calls are
  not stored, so a repeat retries them. The Mac host keeps the last 256
  results. A repeat is the same intent again: a known id with any other
  field changed (a restarted Flipper may reuse an id) is performed as a new
  intent, after one still running under that id, and replaces the stored
  result.
- **Matching.** The Flipper applies a `lookup` only if its `scan_id` is the
  scan on screen, and a `result` only if its `id` is the intent in flight;
  anything else is ignored.
- **Timeouts.** The Flipper waits 10 s for a `result`, then shows an error.
  The host does not time out on the Flipper.
- **Send failures.** A side that cannot send does not leave the other
  waiting: a Flipper whose `scan` does not go out whole shows the tag's
  local facts, one whose `intent` surely did not go out shows an error at
  once, and one whose `intent` may have arrived (only its end was not
  taken) waits for the `result` or the timeout; a host that cannot send a
  `lookup` or `result` closes the port (the Flipper sees the host go) and
  reconnects. A Flipper line cut short is ended by an empty line sent
  before the next one, so the receiver drops the fragment as malformed
  instead of joining it to the next line.
- **Wording.** The host owns all user-visible text. The Flipper renders
  `lines` verbatim and never parses them. Its screen is ASCII-only: each
  control character or non-ASCII character in a string shows as `?`, so
  the host keeps `lines` ASCII where it can.
- **New items.** The Flipper never sends `new` without `prefill: true`, and
  the host refuses to create a spool without `material`. The host names the
  colour from Bambuddy's colour map (`GET /inventory/colors/map`, loaded once
  after the start-up check): `by_material["<detailed type>|<hex6>"]`, then
  `colors["<hex6>"]`, lower-case, alpha dropped. Without a match, or when
  the map failed to load, `color_name` is left out, never a hex string.
  `subtype` is the detailed type without a leading word equal to the
  material, case-insensitive ("PLA Basic" → "Basic", "PETG-HF" stays), as
  on spools an AMS adds; nothing left means no `subtype`. The Flipper's
  `lookup` lines and the host feed still show the full detailed type.
- **Inventory mode.** The host checks `GET /settings/spoolman` and refuses
  to work against a Bambuddy in Spoolman mode: the Mac host answers every
  `scan` with an `error` lookup and every intent with `ok: false`, both
  saying why; the Python bridge exits at start-up.

## Identifiers

`scan_id` and `id` are strings of 1–32 characters from `A–Z a–z 0–9 _ . : -`.
The Flipper uses `s-` / `i-` followed by a zero-padded counter.
